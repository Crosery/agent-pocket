# Issue 规范

> issue 是一件事的主档：开发前先开 issue，写清现象、期望、范围和验收条件；之后每一步进展都以追踪记录留在评论里，PR 合并即关闭。

状态：`current` · 更新：2026-10-09

## §1 开发前先开 issue

**任何 `task/<issue>/<slug>` 分支都必须先有对应 issue**，紧急修复也一样（分支名里要有 issue 号，CI 会检查）。先查重再开新 issue：按端、关键词、报错原文搜索（含已关闭），确认没有同一件事；重复的直接在原 issue 补一条「复现」记录。

**一件事一个 issue**：一个 issue 只描述一件可以独立验收的事。所有者一次提了几件事，能一起验收的放一个 issue，不能一起验收的拆开，互相 `Refs #n`。

用模板开 issue（`.github/ISSUE_TEMPLATE/`）：缺陷报告、需求 / 改进、配置。

生命周期、互相引用和评论格式见 [TRACKING](TRACKING.md)。要点：

| 关联 | 位置 | 要求 |
|---|---|---|
| issue → 分支 | `task/<issue>/<slug>` | 一个 issue 一条 task 分支 |
| PR → issue | PR 正文「关联」段 `Closes #<issue>` | 与分支号一致，CI 的 `pr-contract` 核对 |
| 进展 | issue 评论 | 按 [TRACKING](TRACKING.md) §3 的格式，每个阶段一条 |

**PR 合并进 `stage` 后，它 `Closes` 的 issue 必须关闭，task 分支必须清理。** `issue-lifecycle` 工作流自动关闭并在 issue 与 PR 上各留一条「关闭」记录，`branch-hygiene` 删除远端 task 分支。GitHub 自带的 `Closes #n` 只在合进默认分支 `main` 时生效，不能依赖它。自动化没关上的（工作流失败，或 fork 来的 PR 合并时工作流没有写权限），合并的人当场手工关闭并补记录。已合并的分支不再提交；后续问题开新 issue。

## §2 正文内容

标题：`<模块>：<用户可见的症状或诉求>`，模块取「端」的标签名（见 §4）。

### 缺陷

| 段落 | 要求 |
|---|---|
| 现象 | 实际看到了什么：原文报错、截图、录屏（直接拖进编辑框上传）；动画问题附逐帧图 |
| 复现步骤 | 最小路径，编号，每步写操作与看到的结果；偶发的写复现概率与已知条件 |
| 期望 | 应该是什么样 |
| 影响 | 谁会遇到、多严重、有没有绕过办法；决定优先级 |
| 环境 | 见 §3 |
| 验收条件 | 怎样算修好：可观察的结果 + 要在哪些视口 / 设备 / 环境看 |

### 需求 / 改进

写玩家场景、范围和**不做什么**、涉及的数据表 / 协议 / 存档格式、验收条件。描述问题与期望，不写实现方案（方案写在 PR 的「解决链路」或 issue 的「方案」记录里）。

严重性按真实影响定：线上不可用、存档或数据丢失风险、阻断开发为 P0；主要功能受损或已排期为 P1；其余 P2。未经复现的怀疑标为待确认，不以肯定语气写已证实。

### 线上紧急缺陷（`hot-fix` 标签）

- 定义：正式环境（https://ap.crosery.com）上线后出现的严重问题，如白屏、无法登录或联机、存档损坏、主流程阻断。
- 必须同时打 `hot-fix` 与 `P0`。
- 从 `main` 拉 `hotfix/<issue>/<slug>`，PR 进 `main`，上线后立刻把 `main` 合回 `stage`（[RELEASING](../RELEASING.md)「分支」）。PR 进 `main` 时 GitHub 会按 `Closes #n` 自己关 issue，合并的人补一条「关闭」记录。

## §3 环境与设备

**必填**：

- 分支与完整 commit SHA（`main` / `stage` / `task/<issue>/<slug>`）；
- 地址：本机 dev（`http://localhost:5173`）、预发布 https://prev.ap.crosery.com、正式 https://ap.crosery.com；
- 版本：访问 `<地址>/release.json` 能看到环境、版本和提交（本机 dev 没有，写 `package.json` 的版本）。

**按问题类型补充**（与问题无关的不写，不为凑字段填）：

| 问题类型 | 需要的信息 |
|---|---|
| 画面、界面布局 | 视口尺寸（如 1280×720）、设备像素比、浏览器与版本 |
| 渲染、动画、帧率、卡顿 | GPU / 机型、屏幕刷新率、是否前台真实浏览器（自动化浏览器会限帧，不能用来判断帧率） |
| 战斗、世界 | 所在地图与坐标、队伍与对手、能稳定复现的存档槽或种子 |
| 联机、服务端 | 服务端环境、存档槽；日志只贴相关几行，**不贴令牌、会话或真实玩家数据** |
| 美术资源 | 资源路径、出处的生成任务或参考图编号 |

## §4 标签

| 类别 | 标签 | 用法 |
|---|---|---|
| 类型 | `bug`、`enhancement` | 模板自动带上 |
| 优先级 | `P0`、`P1`、`P2` | 必有其一，受理时按模板里选的定；不确定宁可低一档 |
| 紧急 | `hot-fix` | 只用于线上紧急缺陷，必须同时是 `P0` |
| 端 | `client`、`render`、`battle`、`world`、`content`、`art`、`server`、`deploy`、`docs` | 主端必有其一，跨端的再加其它 |

端的含义：`client` 浏览器端（输入、HUD、界面、存档）；`render` 渲染（地形、光影、粒子、相机、精灵）；`battle` 战斗（规则、数值、战斗界面）；`world` 大世界（生成、地图、遇敌、NPC 行为）；`content` 数据（智灵、招式、事件、文本）；`art` 美术资源；`server` 联机服务端；`deploy` CI、部署、CDN；`docs` 文档与仓库规范。

模板里的「端」「优先级」下拉框只是填写时的约定，**不会自动变成标签**；受理时由维护者按它补标签，并发一条「受理」记录。

## §5 关闭与安全

关闭前 issue 上必须能查到对应 PR 与验证结果（自动「关闭」记录已包含）；不能仅因代码存在或构建成功关闭功能缺陷。放弃、重复、被取代的 issue 先发一条「关闭」记录写明原因再关。做完了就当场关；只剩外部等待的，关掉原 issue、把剩下的一步开成新 issue 写明负责人。每天的巡检会补关 PR 已合并还开着的，给超期和关了没记录的留言（[TRACKING](TRACKING.md) §1）。

安全问题私下报告，不贴令牌、会话、服务器地址或真实玩家数据。
