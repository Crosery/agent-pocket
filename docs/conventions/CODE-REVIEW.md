# 代码审查规范（diff 审查）

> 本仓库的 diff 审查清单：触发时机、逐项检查、结论格式与审查记录位置。

状态：`current` · 更新：2026-10-09

本规范规定**看什么、怎么判、写在哪**；PR 的字段要求与门禁见 [PULL-REQUESTS](PULL-REQUESTS.md)，分支与发布见 [RELEASING](../RELEASING.md)。

## 触发时机

必须在以下情形发生前完成审查：

- 任何要合入 `stage` 的 PR（含文档、脚本、配置）。
- 任何要合入 `main` 的操作（实际是对 `stage` 当下状态的第二道复核）。
- 任何触及部署、CDN、工作流、密钥或服务端存档 / 协议的改动，无论大小。

纯注释错字、纯文档补充可以不逐项走清单，但**结论仍要写在 PR 里**，写「无需逐项审查 + 理由」。

## 必须逐项检查的清单

1. **分支不变量**：来源是 `task/<issue>/<slug>`（热修复是 `hotfix/<issue>/<slug>`）；PR 目标是 `stage`；`stage` 仍包含 `main`（`git merge-base --is-ancestor origin/main origin/stage`）。
2. **发布与部署未被带偏**：`.github/workflows/ci.yml`、`deploy.yml`、`deploy/`、`scripts/static-cdn*` 没有无关改动；推送分支仍然不会触发部署；没有绕过 `stage` 写入 `main` 的路径。
3. **密钥与内部信息**：diff 里没有令牌、密码、会话、SSH 私钥、上传凭据、本机绝对路径、服务器地址或内部域名。密钥只经环境变量或 GitHub Secrets 注入。人眼过一遍新增的字符串，扫描通过不等于没有泄漏。
4. **不硬编码数据**：表、id、名称、玩家可见文案、权重和可调数值在 `content/**/*.json`，代码只放逻辑与 schema；文案在 `content/text/zh-CN/*.json` 经 `t()` 读取；玩家看到的按键名来自按键绑定，不手写进文案。改过的 JSON 用 `python3 tools/content_fmt.py <文件>` 格式化。
5. **共享契约**：`src/shared/types.ts`、`src/shared/contracts.ts` 的改动找全了所有使用方（客户端、服务端、测试）；地块的真值是 `GameMap.infinite`（provider）。
6. **TypeScript 约定**：只用可擦除语法（无 enum、namespace、参数属性）；相对 import 带 `.ts`；JSON 用 `with { type: 'json' }`。
7. **依赖**：没有新增 npm 依赖（Node 内置模块如 `node:sqlite` 除外）；新增生产依赖需要用户同意。
8. **测试与验证**：行为变更带相应测试，能区分修复前后；没有删断言、放宽阈值或跳过用例；PR 里写了真实跑过的命令与结果。
9. **画面与风格**：改动画面的 PR 有同一地点、同一时间的改前改后截图；保持 HD-2D 像素风，没有大幅改变整体风格；玩家可见文本是简体中文。
10. **服务端与存档**：服务端不信任客户端输入；联机协议与存档格式的变更有兼容或迁移方案，旧存档不会读坏；日志里没有令牌或玩家隐私。
11. **文档**：改了流程、数据格式或美术管线的，对应的 `docs/` 同步更新，没有把计划当成事实写进文档。
12. **合并后清理**（合并的人合并后当场核对）：先等这次合并触发的 `issue-lifecycle` 与 `branch-hygiene` 跑完（`gh run list --workflow issue-lifecycle.yml --branch <task 分支> --limit 1`，另一个同理），再核对：PR `Closes` 的 issue 已关闭（`gh issue view <issue> --json state` 是 `CLOSED`），远端 task 分支已删，两边各有一条「关闭」记录。只有工作流失败、issue 还开着时才当场手工关并补「关闭」记录（[TRACKING](TRACKING.md) §3）；工作流还在跑时不手工关，免得留两条。
13. **提交信息**：遵循 [RELEASING](../RELEASING.md)「提交」：`<type>(<scope>): <中文简述>`，一次提交一个可独立回滚的目的，结尾 `Refs #<issue>`；机械搬迁与行为改变尽量分开。

## 产出格式

审查结论以条目写进 PR 评论或 PR 描述，每条包含四要素：

```text
[严重度] 文件:行 — 理由（一句话，指向具体规则或真实后果）— 修法（可执行的具体动作）
```

| 严重度 | 含义 | 处理 |
|---|---|---|
| `阻塞` | 破坏不变量、泄漏密钥、存档不可恢复、绕过发布流程、把计划当成事实 | 必须修完再合并 |
| `应修` | 会带来看得见的缺陷或维护陷阱，但不阻塞本次合并 | 修，或在 PR 里写明为何本次不修 |
| `建议` | 可读性、命名、组织方式 | 作者自行决定 |

## 结论

结论只有三种，逐字使用：

- **阻塞**：存在 `阻塞` 条目，或门禁（`verify`）未通过。
- **有条件通过**：无 `阻塞` 条目，但有未完成的 `应修`（写明条件、责任人和复查方式）。
- **通过**：无未决条目，门禁通过。

不写「基本没问题」「看起来可以」这类模糊结论，也不能用机器 PASS 代替对 diff 的判断。

## 审查记录位置

审查记录写在 PR 里（PR 描述的「审查结论」段，或 `review` 追踪记录评论），至少包含：审查人、时间、被审查的 commit SHA、逐条结论、最终结论。不写进被审查的代码提交本身，也不只存在于聊天记录或本地笔记。合入 `stage` 后，PR 就是这次审查的可追溯存档。

## 与人工验收的边界

代码审查是机器可核验 + 人工判断的第二道筛子，不替代 [RELEASING](../RELEASING.md) 要求的预发布人工验收。审查通过不等于部署授权；部署与发版是独立授权动作。
