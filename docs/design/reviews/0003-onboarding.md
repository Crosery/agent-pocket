# 0003 评审：引导与体验（新手引导 / FTUE）

评审对象：`docs/design/0003-story-and-progression.md`（#41）。基线：`task/41/story_progression`（已合入 integrate/0.2）。
标记：`[verified]` 读代码/内容得出；`[model]` 脚本估算（见 §6）；`[unverified]` 需要实测。未起 dev server，没有截图。

## 1 结论先行

1. **45–53 分钟进 Boss 不算"快速"。** 纯内容（对话 + 战斗 + 走路）只要约 18–24 分钟 `[model]`，其余 20 分钟是"清单跑腿 + 把首发刷到 Lv10"撑出来的。建议：首战 ≤ 5:00；新手中位 ≤ 25:00 开 Boss 战（P90 ≤ 35:00，熟练 ≤ 15:00）；签约 + 出发 ≤ 35:00。手段：删跑腿、商店/补给站挪进前厅、开战等级目标降到首发 Lv8–9。
2. **目标指引的实现前提不成立。** 运行期"当前目标"只读 `trackedQuest` 的单个阶段（`src/client/onboarding/index.ts:58`）；`tutorial.json:10-19` 的 `objective.rules` 运行期没人读，只有测试读。0003 的"每拍一条目标规则""清单三项并行"落不到屏幕上。序章要写成 7 个顺序的 `main` 阶段，不是 +2（§2 B2）。
3. **"上岗清单"有卡死点。** 护士选"不用了"不置 `ob:healed`，店员选"随便看看"不 `teach shop`，小 R 来电又要三项全齐 → 玩家按自己的选择就会卡在 2/3 且没有任何提示（§2 B3）。
4. **57 张弹窗：保留 30 / 改成剧情节拍 7 / 改成情境提示 16 / 删除 4**（§2 I1）。Boss 引导战里教练必须是唯一的"声音"：旧战斗提示全部静默；12 条教练台词有 4 条与 Boss 自带 `say`/`note` 重复，预算压到每场 ≤ 6 条、每条 ≤ 24 字、只在命令菜单出现、不设超时（§2 I2）。
5. **手机端有 3 处现成错误**：开场提示写死键盘键、战斗提示在触屏上显示"A 确认，B 返回"（战斗里没有 A/B）、存档提示在触屏上显示"F5"（§2 I5）。
6. **第 60–150 分钟又回到"徽章计数器"**：第二个 Boss（豆包）约 2.5 小时才有（0003 §3.4），第一章没有 Boss。需要在第一章补一个惊喜点，否则只是把"一直打徽章"从第 1 分钟推迟到第 60 分钟（§2 I7）。

## 2 问题清单

### 阻断

#### B1 时间账：目标分钟数、漏斗、砍/后移清单

**现象。** 0003 §2.2 第 45:00 进 Boss、53:00 签约、60:00 出发。验收是"中位 ≤ 48 分钟"（§8.8 M1-2），对"前期**快速**去打"的原话偏慢。

**证据。**
- 内容时间：按附录 A 的对话框数、战斗回合数、原点镇里的真实距离（家门 → 研究所门 23 格，研究所 → 补给站 16 格，→ 商店 15 格；步速 3.6 格/秒 `content/config.json:3`）累加，0003 的节拍 B0–B14 只要 **17.9 分钟**，乘 1.35 的新手系数 24.2 分钟 `[model]`。三次"跑腿"（B8–B10）合计走路不到 30 秒，花的是对话和菜单。
- 等级时间：首发 Lv5 → Lv10 约 10 场同级野战（`docs/balance.md:170-176`：Lv5–9 每级 1.5–2.4 场）；`grassRateMultiplier 0.18` 下约每 56 步一战（README），每场连走带打约 65–75 秒 → **约 11–12 分钟纯刷** `[model]`，而 0003 §3.3.2 要求开局 Lv10 + 文心 Lv7。
- 两者相加 + 新手停顿 ≈ 45 分钟，即 0003 的数字。**时间不是内容撑出来的，是"缺等级"和"跑腿"撑出来的。**

**改法。**
- 目标：首战 ≤ 5:00（0003：11:00）；新手中位开 Boss ≤ 25:00；熟练 ≤ 15:00；签约 + 出发 ≤ 35:00；`tests/opening.test.ts` 加"脚本图最短路径时长 ≤ 12 分钟"（按 §6 的模型参数）。
- 开战队伍：首发 Lv8–9、文心 Lv6，体验版 Lv12 → Lv10；用 `scripts/boss-sim.ts --tier=story --party=opening` 重算 §3.3.2 的胜率表。依据：每缺 1 级 ≈ 一场 65–75 秒的野战。`[unverified]` 脚本战斗的经验量，交数值评审。
- 经验来源：序章经验 ≥ 70% 来自剧情战（零、陪练、文心、路线一训练家、阿转），草丛只负责文心；遇敌率不动（遵守"只降不升"）。

#### B2 目标指引：运行期不读 `objective.rules`，且只有一个目标

**现象。** 0003 §3.2 假设"每拍都有目标规则"，§8.6 `opening.test.ts` 也这么验；§3.1 又要"清单三项并行"。

**证据。**
- `onboarding/index.ts:57-72` 的 `refreshObjective` 用 `overworld.questNavigation`；`pickObjective`（`logic.ts:50`）只被 `tests/onboarding.test.ts`、`tests/dev-scenarios.test.ts` 调用。`tutorial.json` 里 `starter/rival/typeLesson/route/catch/heal/gym1` 七条规则是死数据。`[verified]`
- 当前目标 = `save.trackedQuest` 一个任务的一个阶段的一个 `target`（`quest-navigation.ts:30-36,243-246`）。`applyQuest`（`save-ops.ts:107`）只在"没有被追踪的任务"时才切换，所以 `ds-prep` 这类新任务不会抢走 `main` 的追踪。`[verified]`
- 现状：`professor` 脚本在 `chooseStarter` 后直接 `quest main stage 1`（`npcs/story.json` prologue[1] else[12]），选完搭档那一刻箭头就指向开源林镇道馆，零和阿灵都没有箭头。`[verified]`
- `main-progress`（`scripts.json:24`）末项 `atLeast 0 → stage 1`，加上全库 15 处写死的 `"quest":"main","stage":N`，插入阶段时全部要平移；否则 `include main-progress` 会把序章阶段一口气跳过（`applyQuest` 只进不退）。`[verified]`
- HUD 左上角同时有「当前任务」（`hud.ts:32-44`，文案 `{quest}：{stage}`）和「当前目标」（`onboarding/view.ts:91-96` 插在它后面），同一句话显示两次。`[verified]`（代码层面；未截图）

**改法。**
1. 序章写成 7 个顺序阶段，每阶段 1 个 `target`、摘要 ≤ 14 字（`quests.json:main`，旧阶段整体后移 7）：

```json
[
 {"text": "妈妈说图灵博士在找你。去镇上的研究所拜访他吧。", "target": "town:origin:lab"},
 {"text": "挑一位搭档，再和零切磋。", "target": "origin-lab:rival"},
 {"text": "找阿灵上一节属性课。", "target": "origin-lab:aide-2"},
 {"text": "去草原，找那只抢答的智灵。", "target": "route:route-1:1"},
 {"text": "回研究所，从楼梯下到机房前厅。", "target": "origin-lab:stairs"},
 {"text": "叫醒核心机柜上的 DeepSeek。", "target": "origin-lab-b3:core"},
 {"text": "回研究所向博士复命。", "target": "origin-lab:professor"}
]
```

2. 迁移：`migrations.json:mainStage["1"]` 的位移是 +7（0003 §6.7 写的 +2 不够）；`main-progress` 的 12 个常量和另外 15 处 `quest main stage` 一并改；`tests/opening.test.ts` 改成"阶段链从 0 走到最后一个序章阶段，每阶段 `target` 可达"，不再验 `objective.rules`。
3. 清单不再并行。需要"任意顺序"的事（商店、补给站）不进目标条。
4. 序章期间隐藏 `.ap-quest`，只留 `.ap-objective`（见 §I4）。

#### B3 清单卡死点

**证据。**
- `nurse` 脚本（`scripts.json:2`）只在选"拜托了"分支里 `setFlag ob:healed` + `setRespawn`；满血的玩家选"不用了"，清单永远差一项。`[verified]`
- `clerk` 脚本只有选"买卖道具"才 `teach shop`；选"随便看看"不会置 0003 的 `ob:shopped`。`[verified]`
- 0003 §3.2 B11：三项齐全才来电，`ds-tide` 入口要 `ds:called`（§8.2）。没有任何提示告诉玩家缺哪一项。

**改法。** 删除 shop/heal 跑腿（§B1），来电条件改为 `{"on":"dex:caught","when":{"noFlag":["ds:called"]}}`；若仍保留任何"多项清单"：旗标必须在进入交互时置位，不能依赖玩家的选择；目标条显示"x/3"并指向第一个未完成项；`tests/opening.test.ts` 对每个选项分支验证"无论选什么都能推进"。

#### I2 DeepSeek 引导战：读字量、教练条、暂停

**现象。** 战斗里有三层字同时在跑：引擎消息（每回合 3–5 条）、Boss 自带 `say`/`note`、0003 的教练台词，外加旧战斗提示卡。

**证据。**
- 教练 12 条（附录 B `coach`）。按触发器与"每条每场一次，谷时开始最多 3 次"（§3.3.3）计，一场 12 回合最多 **16 条**，平均超过每回合一条。`[model]`
- 4 条与现有 Boss 文本重复：`peakWasted` ↔ 打在高峰期时引擎自动播的 `note: boss.deepseek.busy`（`bosses.json:122`）；`couponUsed` ↔ `boss.deepseek.coupon`；`hike` ↔ `boss.deepseek.hike`；`enrageWarn` ↔ `boss.deepseek.enrageWarn`（`text/zh-CN/boss.json`）。同一件事读两遍。
- `superEffective` 42 字、`start` 36 字、`peakWasted` 33 字，超过一行；效果拔群本来就有引擎消息 + 音效 + 招式详情。
- 时段栏已经常驻在对手名牌上（`status-panel.ts:setBoss` → `model.ts:bossPanelInfo`，`states` 型 chip），但只有文字、没有"还剩几回合"。

**改法。**
